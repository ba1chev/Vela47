# Change management

The infrastructure is treated as a product with versions, not as configuration edited in place. Every change to what runs on AWS is a release (see `release_process.md`), and every release declares what kind of change it is. The pipeline holds it to that declaration twice: CI against the changed files, the deployment against the Terraform plan.

## One codebase, three environments

dev, staging and prod run the same modules from the same release. They differ only in the values of their root modules (`deploy/terraform/environments/<environment>/`):

| | dev | staging, prod |
|---|---|---|
| Instances | 1 × t4g.small, scaled to 0 at night and on weekends | 2 × t4g.medium in two zones, up to 4 |
| Server tasks | 1 | 2 |
| NAT | t4g.nano NAT instance | NAT gateway |
| Database | Single-AZ, 1 day of backups, no final snapshot | Multi-AZ, 14 days of backups, final snapshot, deletion protection |
| Deployments | ROLLING | CANARY |
| Logs | 7 days | 30 days |

Staging and prod are identical apart from their name, domain and address range. A unit test (`test_terraform_environments.py`) fails if they drift apart.

## Configuration

There is one configuration schema, `Config` in `app/server/config.py`. Values come from three places:

- **Code**: anything that is the same everywhere (models per platform, limits, prompts).
- **Terraform root of the environment**: anything that differs per environment (sizes, domain, strategy). The task definition passes them to the server as `VELA47_*` variables.
- **Secrets Manager**: secrets only (`vela47-<environment>/app`, generated by Terraform, and the RDS-managed database secret). The Tavily key comes from the GitHub environment secret `TAVILY_API_KEY`.

A configuration change is therefore an infrastructure change and goes through the same release, review and deployment as code. There is no configuration service and no tfvars file.

## Kinds of change

`deploy/release.yaml` declares two classes per release.

| `infrastructure` | Meaning | May ship with code |
|---|---|---|
| `none` | nothing in the AWS environments changes | yes |
| `additive` | new resources, more capacity, new settings the running release does not notice | yes |
| `breaking` | removing, shrinking or replacing something the running release may use | no, alone and as a new major version |

| `database` | Meaning | May ship with code |
|---|---|---|
| `none` | no migration | yes |
| `expand` | new tables, nullable columns, indexes: the previous release keeps working | yes |
| `contract` | dropping or renaming what the previous release still reads | no, alone and as a new major version |

Rules enforced in CI (`ReleaseRules`):

- Terraform changes of the AWS environments need `infrastructure` other than `none`; a new release declares only changes it makes.
- New migrations need `database` other than `none`, and the other way round.
- `breaking` and `contract` releases change no application code and raise the major version.

Rules enforced at deployment (`PlanGuard`):

- No plan may delete or replace an RDS instance or an S3 bucket.
- The `vpc` and `database` roots may change only in a release that declares an infrastructure change. A change anyway means drift made outside Terraform, and the deployment stops.
- They may delete something only in a `breaking` release.

## Release patterns

**Expand, then contract.** A change that removes or renames something is split across releases, so each release runs on what the one before it left:

1. Release N (`additive` / `expand`): add the new resource or column. Code that uses it may ship in the same release, because the deployment applies Terraform and the server migrates the schema before the new tasks take traffic.
2. Release N+1: move every reader to the new thing.
3. Release N+2 (`breaking` / `contract`, new major version): remove the old one.

**More capacity.** A release that needs a larger instance, more memory or another task is `additive`. The new size is applied before the new tasks start, and the capacity provider adds instances when tasks do not fit.

**Less capacity.** Shrinking is `breaking`. It ships alone, after the release that no longer needs the capacity runs in prod.

**New resources** (a queue, a bucket, a second service) are `additive`. They ship with the code that uses them, or before it.

## Stateful resources

The RDS instance is the only state the environments keep.

- **Migrations** are Alembic revisions in `db/migrations/versions/`. The server applies them when it starts, inside one transaction behind an advisory lock, so a failed migration leaves the schema as it was. During a canary deployment the old tasks run on the migrated schema, which is why every revision must keep working with the release before it (`expand`).
- **Backups**: RDS keeps automated backups for point-in-time restore (1 day in dev, 14 in staging and prod). Before every deployment to staging or prod the pipeline takes a manual snapshot named `vela47-<environment>-<version>-<run>`. Destroying a staging or prod instance leaves a final snapshot.
- **Restore** is a manual operation and the last resort. Restoring creates a new instance, which then replaces the old one in the `database` root. Prefer a forward fix: a new release with a migration that repairs the data.
- **Engine upgrades**: minor versions are applied by RDS in the maintenance window. A major version upgrade is a `breaking` release, done with RDS Blue/Green Deployments.

## Approvals and review

- Every change is reviewed in a pull request. Required checks: the CI jobs.
- dev is deployed without approval. staging and prod need an approval from the required reviewers of their GitHub environment, given after reading the preview of the plan.
- The permissions of the pipeline itself (`shared/iam`) and the account-wide roots (`shared/*`) are applied by hand. The pipeline cannot change them.
